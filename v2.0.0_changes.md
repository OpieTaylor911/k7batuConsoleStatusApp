# Task: Modernize the Existing GTK3 uConsole Dashboard UI

You are working inside an existing GTK3 application for a ClockworkPi uConsole CM5. Do not rewrite the application from scratch and do not migrate it to GTK4, Electron, React, Qt, or a web UI.

The goal is to modernize the current GTK3 dashboard so it looks like a polished embedded field-console application rather than a traditional Linux desktop utility.

## Primary Goal

Refactor and restyle the existing GTK3 interface into a compact, professional dashboard optimized for the uConsole display.

Use a visual style inspired by modern dark dashboards such as GitHub's dark UI and the design patterns used by the `uconsole-cloud` project, but implement everything natively in GTK3.

Preserve the existing application logic, service detection, hardware detection, launchers, commands, subprocess handling, and backend behavior wherever possible.

Focus primarily on:

* layout
* navigation
* visual hierarchy
* reusable widgets
* GTK CSS
* dashboard cards
* device status rows
* metrics
* spacing
* typography
* icons
* responsiveness on the uConsole display

Do not remove existing functionality unless it is clearly obsolete or duplicated.

# Plugin Architecture — Important Existing Design Requirement

This application uses a plugin model. Treat plugins as first-class application modules, not just button extensions.

A plugin may contain BOTH:

* complete GTK3 UI code
* Python backend / hardware / service / launcher logic

Do not collapse plugin functionality into the main dashboard.

The redesigned UI must preserve and improve this plugin architecture.

## Plugin Concept

Each plugin should be capable of providing some or all of the following:

```text
Plugin
├── metadata
├── GTK3 page / panel
├── Python logic
├── hardware detection
├── service status
├── commands / launchers
├── configuration
├── icons/assets
└── optional periodic refresh logic
```

Examples may include:

```text
plugins/
    gps/
```

# Plugin Registration

Plugins should register themselves with the main application through a clear interface.

Conceptually, a plugin may expose metadata similar to:

```python
PLUGIN_INFO = {
    "id": "gps",
    "name": "GPS / Navigation",
    "icon": "gps.svg",
    "category": "Navigation",
    "order": 30,
}
```

and an entry point similar to:

```python
class GPSPlugin:
    def get_id(self):
        return "gps"

    def get_name(self):
        return "GPS / Navigation"

    def get_icon(self):
        return "gps.svg"

    def build_page(self, app_context):
        return Gtk.Widget

    def activate(self):
        pass

    def deactivate(self):
        pass

    def refresh(self):
        pass

    def shutdown(self):
        pass
```

This is an architectural example only.

If the application already has a plugin API, use the existing API rather than inventing an incompatible one.


rather than:
